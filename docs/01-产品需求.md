# 产品需求

## 背景与第一性原理

世界设定常散落在笔记里。作者写到封城才发现税粮、补给和节日日期互相影响。Agent可以描述制度，但每次重新推算容易丢失单位、前提和未确认假设。本插件保存可回读的规则与有限确定性计算，让变化有出处。

生成式Agent擅长理解和提出方案，反复重建相同界面、引用及计算则增加等待与核对成本。固定专业结构承载可确定执行的部分，包内Skill承载方法，Agent完成理解和创作，作者负责取舍。这里不假设动态UI每次点击都需要模型，也不以JSON字节推算Token费用。

独立插件的理由是专业状态具有自己的生命周期和交付：calendar 1—N marker；rule N—N premise；scenario N—N assumed rule；scenario 1—N event N—1 resource。这些关系不应挤入宿主通用作品Schema；作者不需要该任务时无需接触此工作面。

## 用户目标

读取固定正文与设定→建立明确历法与制度假设→核对日期和依赖→在固定情景计算资源→解释不足及影响→交给规划或宿主候选→按新依据继续。

用户可以只说目标，Agent准备专业结构并回读。手工编辑保留为可选入口，作者不必重复填写会话已有资料。

## 首版范围与非目标

正式正典归宿主；历史与经济判断归作者和外部Agent。本包只计算明确声明的虚构历法及整数资源，不推断真实地理、社会科学结论或自动修改正典。地图及行程投影复用小说图鉴，故事事件偏序复用小说规划。

首版必须完成全部声明动作、固定来源与版本、可理解工作面、Skill、CLI/MCP、导出及恢复，不以空页面和通用JSON编辑器代替专业能力。付费生成、外部发送、正文采纳和定稿分别决定。

## 成功标准

相同固定输入得到可解释的确定性结果；新资料不覆盖旧依据；无GUI可完成业务；作者能看见完整成果和未知范围；安装、启停、卸载重装与旧修订回读均有证据。实际平台与失败记录见[08](08-实施计划与验收记录.md)。

## 研究方法

固定GitHub源码、实际许可证、重点算法及公开SaaS页面。参考与复制分别判断，不执行上游插件。研究来源见[固定来源](research/sources.json)及[研究结论](research/README.md)，未取得的页面不作为功能事实。
